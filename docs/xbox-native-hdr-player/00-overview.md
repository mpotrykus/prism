# Xbox Native HDR Player — Planning Briefing

**Goal:** design and build a native DX11 video player for the Xbox UWP shell (`uwp/PrismUwp/`), with real HDR10 support, to replace the current `<video>`+hls.js fallback in `plex-player.js`. Reference architecture: `moonlight-xbox` (this machine's other Xbox UWP project, C++/CX, real-time game-streaming client) — not code to reuse directly (different product, different constraints), but a proven reference for "DX11 + HDR10 + hardware video decode on this exact console/OS combination."

**How to use this folder:** this is pre-digested research, not a plan. Read all four documents below, then design the actual architecture/implementation plan from scratch — nothing here should be treated as a decision already made.

- [`01-moonlight-xbox-dx11-pipeline.md`](01-moonlight-xbox-dx11-pipeline.md) — how moonlight-xbox does D3D11 device/swapchain setup, HDR10 output (two-layer: UWP `HdmiDisplayInformation` display-mode switch + DXGI `SetColorSpace1` per-frame tagging), ffmpeg/D3D11VA hardware decode → texture, and its render/present loop.
- [`02-moonlight-xbox-nis-compute-shader-pattern.md`](02-moonlight-xbox-nis-compute-shader-pattern.md) — a closed (never-merged) PR against moonlight-xbox adding a DX11 compute-shader upscaling pass. Not directly useful for upscaling (Prism doesn't need it), but a concrete worked example of "how to wire a compute shader into this exact render pipeline" — the same mechanics (UAV/SRV hazard tracking, resource handoff, constant buffer setup) would apply to a compute-shader-based HDR tone-mapping pass if one turns out to be needed.
- [`03-prism-uwp-shell-and-android-bridge-contract.md`](03-prism-uwp-shell-and-android-bridge-contract.md) — the exact JS↔native contract Android's `NativePlayerPlugin`/`PlayerActivity` already implements (method names, event names, payload shapes), which a new Xbox native player should replicate the *shape* of (not the Capacitor transport — Xbox will need WebView2 message-passing instead). Also documents the current Xbox shell's state: WebView2 initialization, gamepad-to-keydown forwarding, and confirms **no player bridge of any kind exists yet**.
- [`04-relevant-lessons-from-memory.md`](04-relevant-lessons-from-memory.md) — prior hard-won lessons from this project's build history that bear directly on this task: the WebView-suspends-JS-timers-during-native-playback gotcha (likely to recur on Xbox's WebView2), the 5-layered-bug audio-track-switch saga (a type-coercion bridge bug that would silently recur on any new native bridge), the existing bandwidth-based Auto-ABR contract a native Xbox player should also satisfy, and this project's current (deliberately scoped-out) HDR posture on Android.

## Known constraints going in (from `CLAUDE.md`, not re-derived here)

- **No backend/proxy** — Plex auth token travels as a URL query param, not a header (Plex won't answer a preflight otherwise). Native decode needs no custom HTTP header injection because of this.
- **Xbox shell is WebView2**, not a raw browser — no native HLS support (same gap as desktop Chrome), which is *why* a native player is worth building at all (the JS/hls.js fallback has a real ceiling here, not just a nice-to-have upgrade).
- **Two unresolved upstream WebView2-on-Xbox risks**, not yet validated on real hardware: a gamepad-focus-trap bug, and a Store-certification snag with fixed-version WebView2 runtimes. Worth a quick validation pass early, since either could constrain how the native player's UI chrome and focus model interact with the WebView2 host.
- **Deployment**: use Visual Studio's "Remote Machine" debug target against a paired, Dev-Mode-enabled Xbox — confirmed working, sidesteps the atomic-dependency-closure problem of manual Device Portal sideload. `xbox-build.mjs` builds Release only (Debug's framework deps don't sideload cleanly).
- **Package manifest currently has no HDR-related capability declared**, and `hevcPlayback`/PlayReady `DeviceCapability` entries are explicitly not yet requested (flagged in a code comment as "add once native playback is implemented").
- Android's own HDR support is intentionally scoped to "auto-skip SDR shader effects on HDR content" — **not** full passthrough/tone-mapping. This Xbox effort would be the first leg of this project to attempt genuine HDR10 output. Per project memory, the user's explicit expectation is full HDR support on Xbox once a native pipeline exists — treat it as a real target, not a stretch goal.
