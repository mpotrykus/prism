# Relevant Prior Lessons From This Project's Build History

Pulled from this machine's persistent memory for the Prism project. These are point-in-time observations from past sessions, not live code state — verify specifics against current code before relying on a file:line citation from here.

## HDR posture today, and why Xbox is expected to be the feasible leg

From memory `shader-color-boost-hdr` (2026-08-06): Android's only HDR-related behavior today is `PlayerActivity.isHdrContent()` auto-skipping the SDR-tuned shader/Color-Boost GL effects pass on real HDR sources (checks `Format.colorInfo` for `COLOR_SPACE_BT2020`/`COLOR_TRANSFER_ST2084`/`COLOR_TRANSFER_HLG`) — this is **not** HDR passthrough or tone-mapping, just "don't apply an SDR effect on top of HDR content." True HDR passthrough/tone-mapping was deliberately scoped out, not attempted and abandoned.

Explicit correction recorded from a prior session (user pushback against an earlier draft that lumped Xbox in with web's genuine dead end): **web has no realistic HDR path** (browsers can't do this), but **Xbox does** — real HDR passthrough is proven achievable from a native UWP app on this exact hardware/OS, demonstrated by hands-on work on `moonlight-xbox`. The blocker for Prism's Xbox leg has only ever been that it still runs WebView2's `<video>`+hls.js (same ceiling as web), not that Xbox/UWP itself can't do HDR. **The user's explicit stated expectation: "I would expect the xbox/uwp port to fully support hdr" once a native pipeline exists** — this is a real target for this effort, not a stretch goal to hedge on.

Also relevant: `web`/Xbox currently has no way to read a `<video>` element's real color-space/transfer info from a browser without WebCodecs — this constraint disappears entirely once Xbox has a native player, since native code can read the real decoded format directly (as Android's `PlayerActivity.isHdrContent()` already does, and as moonlight-xbox's `frame->color_trc` check does).

## NIS PR as a DX11 compute-shader integration reference

From memory `moonlight-xbox-nis-upscaling-pr`: moonlight-xbox has a (never-merged, see `02-moonlight-xbox-nis-compute-shader-pattern.md`) PR adding NVIDIA Image Scaling via a DX11 compute-shader pass, hooked into its `VideoRenderer` via a new `VideoUpscaler` class. Noted at the time as "worth revisiting once Prism's Xbox native pipeline gets built, as a possible upgrade path" — specifically relevant if Prism's shader-upscaling feature (`shaders.js`'s Anime4K/CAS fragment shaders) is ever ported to native Xbox, since NIS's compute-shader approach has access to shared-memory patterns a WebGL fragment shader can't get. Separately useful now as a mechanics reference for any future compute-shader-based HDR tone-mapping pass, since the resource-binding/hazard-tracking/dispatch patterns are identical regardless of what the compute shader actually computes.

## The WebView-suspended-during-native-playback gotcha (Android-confirmed, Xbox-unverified)

From memory `android-webview-paused-during-native-playback` (2026-08-13): confirmed on a real Android device that while `PlayerActivity` (native ExoPlayer screen) is foregrounded, the Capacitor `BridgeActivity`'s WebView is paused, and `WebView.onPause()` suspends **all** network resource loading, not just JS timers — verified by attaching to the WebView's remote-debugging socket and finding a plain `fetch()` never resolved while backgrounded. This meant Plex `/:/timeline` progress reporting (which this codebase's architecture keeps entirely in JS, not native) silently never reached Plex for the whole duration of native playback.

**Fix applied**: moved `/:/timeline` reporting into native Java (`PlayerActivity.reportNativeTimeline`, using `PlexHttp`'s plain `HttpURLConnection`), a deliberate, narrow exception to this codebase's "one protocol implementation in JS, not one per platform" preference — forced specifically by the WebView limitation, not a design choice.

**How this applies to Xbox**: WebView2 is a different engine (Chromium-based, not Android's system WebView) hosted in a different lifecycle model (a XAML UWP page's control, not an Activity being backgrounded) — **it is not safe to assume WebView2 has the same "network suspended while a native surface is foregrounded" behavior**. This needs to be verified empirically on real Xbox hardware before deciding whether Prism's Xbox native player can keep `/:/timeline` reporting in JS (matching this codebase's normal architecture) or needs the same native-side duplication Android required. Don't assume either way going in.

## The 5-layered audio-track-switch bug saga — a template for what will bite a new bridge

From memory `audio-track-switch-decision-endpoint-fix` (2026-08-13): Android's audio-track/version/quality-cap switching took **five independently-layered bugs** to fully fix, discovered one at a time only because each fix was verified against real server/device state before moving to the next. Full detail in `03-prism-uwp-shell-and-android-bridge-contract.md` §4, but the pattern-level lessons worth carrying into an Xbox bridge design from day one (not rediscovering the hard way):

1. **Plex's Media Decision Engine never re-evaluates without an explicit `/decision` call** before `/start` — any restart-based reload must call `/decision` with identical params first.
2. **`Uri.Builder.path()`-style URL builders can silently corrupt URLs containing a literal `:`** (Plex's `/video/:/transcode/universal/decision` endpoint) by re-encoding it to `%3A` — build such URLs via plain string substitution, not a path-segment API, on whatever platform (this generalizes beyond Android's `Uri.Builder` — worth checking whatever URI-building API .NET/WinRT uses on Xbox for the same footgun).
3. **Manual switches can race the ABR monitor's own autonomous reloads** — needs a monotonic generation counter so a slower-resolving stale reload can't stomp a newer one's result.
4. **Even with client-side stale-result rejection, overlapping requests sent to Plex's server can still corrupt server-side transcode-session state** — needs actual request serialization (one in-flight reload at a time, coalescing queued requests to the latest), not just discarding stale responses client-side.
5. **A numeric Plex id (e.g. `partId`) crossing a typed JS↔native bridge without explicit string coercion can silently arrive as `null`** on the native side (Capacitor's `PluginCall.getString()` returned `null` for a JSON number, no error). This was the actual final blocker and defeated four rounds of otherwise-correct fixes to bugs #1-4 before being found.

**Direct implication for an Xbox WebView2 bridge**: whatever message-passing mechanism is used (`postMessage`/`WebMessageReceived`, `AddHostObjectToScript`, or similar), audit it explicitly for the same numeric-id-silently-becomes-null failure mode before shipping — this is exactly the kind of bug that "looks correct" in code review and only surfaces against a real server under real switching sequences.

## Existing Auto-ABR / quality contract an Xbox native player should also satisfy

From memory `auto-quality-abr-feature` (2026-08-08): bandwidth-based automatic quality switching plus a manual Quality Cap/Version picker exist on both web and Android today, walking the same fixed preset ladder via the existing manual-switch restart mechanism (Plex has no multi-variant HLS manifest to switch within — every quality change is a full transcode-session restart). Full technical contract (tuning constants, decision thresholds, bandwidth-signal sourcing) is documented in `03-prism-uwp-shell-and-android-bridge-contract.md` §4. Relevant here mainly as a reminder: this is an existing, tuned, cross-platform feature contract a new Xbox player is expected to participate in, not something to redesign from scratch — the bandwidth-signal source will necessarily be Xbox/DX11-specific (there's no ExoPlayer or hls.js to read from), but the decision logic, thresholds, and restart mechanism should mirror the existing implementation.
