# Prism

A standalone rewrite of a Netflix-style Plex browsing dashboard, targeting **web, Android, and Xbox**, with **remote (Amazon Fire TV/Fire Stick), touch, and controller (Xbox gamepad)** input support. The app itself is plain HTML/CSS/JS custom elements (no UI framework) — but it's built via **Vite** (`vite.config.js`, `base: "./"`, outputs to `dist/`) and wrapped natively per platform: **Capacitor** for Android (`android/`, package `com.mpotrykus.streaming`), a **UWP + WebView2 shell** for Xbox (`xbox/PrismXbox/`). Plain `dist/` output still works as a directly-served PWA for the web target.

## Origin

The UI (`plex-netflix-card.js`) started life as `custom:plex-netflix-card`, a hand-written vanilla-JS Home Assistant Lovelace custom card running on a home server (`raspi-server`), browsing a personal Plex library with Netflix-style rows, a hero banner, search, Kids Mode, AI-generated genre rows, etc. That HA-hosted version is the **feature-complete reference implementation** — extensive build history (every feature, every bug, every fix) lives in this machine's memory for the `Desktop` project, not in this repo. If you need to know *how* an existing feature was originally built or why a specific decision was made, check there first — see `reference_dashboard_history` in this project's memory.

This repo is the rewrite: pull the card out of Home Assistant entirely so it can run as its own installable app on multiple platforms/input modes HA's Lovelace panel never had to support.

## Current state

- `package.json`/`vite.config.js` — the Vite build. `npm run dev`/`build`/`preview` for the plain web target; `npm run android` runs `cap sync android` then a Gradle debug build; `npm run xbox:sync` builds and copies `dist/` into the Xbox shell's `www/` folder only (no `.msix`, same as `cap sync` not building an APK by itself); `npm run xbox:build` chains that plus an actual MSBuild restore+build, producing a sideloadable `.msixbundle` under `xbox/PrismXbox/AppPackages/`. MSBuild is located via `vswhere` (`scripts/xbox-build.mjs`), not a hardcoded Visual Studio path.
- `android/` — a committed, working Capacitor Android project (`com.mpotrykus.streaming`). Hosts the same web app inside a `BridgeActivity` WebView, plus a native `NativePlayerPlugin`/`PlayerActivity` (Media3 ExoPlayer) bridged in from `plex-player.js` for native-grade playback — see "Native playback" below.
- `xbox/PrismXbox/` — a UWP project hosting the same web app in a WebView2 control, targeting the Xbox device family. **Shell only so far**: no native playback bridge yet, still relies on `plex-player.js`'s `<video>`+hls.js fallback. Two open upstream WebView2-on-Xbox risks (a gamepad-focus-trap bug, and a Store-certification snag with fixed-version WebView2 runtimes) need validating on real hardware via Xbox Dev Mode before a native MediaPlayerElement bridge or Store submission is worth building.
  - **Signing:** `npm run xbox:build` produces an unsigned package unless a matching cert exists — Xbox Dev Mode sideload rejects unsigned packages outright (`0x800B0100`). `PrismXbox_TemporaryKey.pfx`/`.cer` (self-signed, `CN=mpotrykus`, matching `Package.appxmanifest`'s `Identity Publisher`, password-less, ~20yr validity) are committed alongside the project — same convention Visual Studio uses by default for new UWP projects, referenced from `PrismXbox.csproj` via `PackageCertificateKeyFile`/`PackageCertificateThumbprint`. Signing the package is necessary but not sufficient: the Xbox console itself also has to **trust** this cert's root before it'll install the package — a signature check on an untrusted self-signed root fails differently (chain-validation error, not the "no signature" error) but still fails. Install `PrismXbox_TemporaryKey.cer` as a trusted certificate on the target console via its Device Portal (`https://<xbox-ip>:11443`, paired from the Dev Home app) before sideloading the `.msixbundle` — this is a one-time, per-console, manual step that can't be scripted from here.
  - **Deployment: use Visual Studio's "Remote Machine" debug target, not manual Device Portal sideload.** Confirmed working. A manual Device Portal upload of the `.msixbundle` requires separately uploading every framework dependency under `AppPackages/.../Dependencies/x64/` (5 files for this C# shell: `Microsoft.VCLibs.x64.14.00[.Desktop]`, `Microsoft.UI.Xaml.2.8`, `Microsoft.NET.Native.Framework.2.3`, `Microsoft.NET.Native.Runtime.2.3`) **in the exact same install request** — Windows validates the whole dependency closure atomically, so a request missing even one fails entirely and nothing from it persists, which makes adding dependencies one-at-a-time across separate attempts (in response to each new "framework could not be found" error) never converge. Opening `PrismXbox.sln` in Visual Studio and deploying to the paired Xbox as a Remote Machine target sidesteps all of this - VS provisions every framework dependency itself. `xbox-build.mjs` still builds **Release**, not Debug, since Debug's framework dependencies (`Microsoft.NET.CoreFramework.Debug.2.2`, `Microsoft.VCLibs...Debug.14.00`) are SDK-only debug redistributables that don't sideload cleanly even via the correct atomic-request approach.
  - **The two .NET Native framework dependencies are avoidable, just not for free.** `moonlight-xbox` (this machine's other Xbox UWP project, C++/CX) needs only `Microsoft.UI.Xaml`+`Microsoft.VCLibs` per its own README - no `.NET Native Framework/Runtime` at all, because those two are purely a byproduct of this shell being C#. A future C++/WinRT rewrite of this trivial WebView2 shell would drop the dependency count from 5 to 2 permanently, matching moonlight's proof - worth considering deliberately later, not a Phase 3 blocker now that Remote Machine deploy works.
- `index.html` — shell: mounts `<streaming-plex-signin-modal>` and `<streaming-settings-modal>`, then boots.
- `app.js` — bootstrap. Registers the service worker, creates a detached `<plex-netflix-card>`, wires `open-settings`/`settings-saved`/`request-plex-reauth`/`plex-connected` events between the card and the two modals, and opens the Plex sign-in modal (blocking) at boot if no server is configured yet (`window.StreamingSettings.isConfigured()`).
- `vault.js` (`window.StreamingVault`) — encrypts the sensitive config fields (`plex_token`, `plex_account_token`, `youtube_api_key`, `openrouter_api_key`) at rest instead of plaintext localStorage, using a non-extractable AES key stored in IndexedDB. Deliberately *not* gated behind WebAuthn/biometrics (an earlier version was) — `plex_token` now comes from Plex's own PIN-based sign-in rather than being hand-typed, so there was no local secret-entry step left to justify prompting Windows Hello/Android biometrics on every save and load.
- `plex-auth.js` (`window.StreamingPlexAuth`) — talks to `plex.tv` directly: the PIN-based sign-in flow (`requestPin`/`pollPin`/`buildAuthUrl`), server discovery (`discoverServers`/`resolveBestConnection`), and Plex Home profile listing/switching (`getHomeUsers`/`getCurrentUser`/`switchHomeUser` — see "Plex Home profiles" below).
- `plex-signin.js` (`<streaming-plex-signin-modal>`) — the sign-in UI built on `plex-auth.js`. Gates the whole app at boot (blocking, no close button, until a server is connected); reachable again afterward, non-blocking, via Settings' "Reauthenticate" button.
- `settings.js` (`window.StreamingSettings` + `<streaming-settings-modal>`) — everything *not* secret (plex_url, machine_id, sections, tuning knobs) lives in plain localStorage; merges with decrypted vault secrets into the "full config" the card expects via `setConfig()`/`refreshConfig()`. This is the replacement for HA's Lovelace card-config YAML editor. Plex sign-in itself lives in `plex-signin.js`, not here — this modal only shows connection status and a "Reauthenticate" button that delegates to it.
- `plex-netflix-card.js` — the actual UI. Ported near-verbatim from the HA card; confirmed already decoupled from `hass`/`callService` (grepped clean) — it now reads everything from `this._config` the same shape `settings.js` produces. Also owns the Plex Home profile switcher (sidenav "Profile" item, only shown when the signed-in account has more than one Home profile) — see below. A poster or the hero's Info button now opens an in-app title-info overlay (`_openTitleInfo`/`_closeTitleInfo`, same internal-overlay pattern as the profile/PIN overlays) instead of navigating away — its Play button hands off to `plex-player.js`.
- `plex-player.js` (`window.StreamingPlayer`) — shared playback module used by the title-info overlay's Play button. Detects native capability via `Capacitor.isNativePlatform()`; on Android, calls into the `NativePlayerPlugin` bridge (see `android/` above); everywhere else, falls back to a full-screen `<video>` overlay with `hls.js` for Plex's HLS transcode sessions. Both paths share the same Plex `/:/timeline` progress-reporting loop, driven from this module (not from native code) — see "Native playback" gotcha below.
- `sw.js` — network-first service worker for the app shell (deliberately *not* cache-first: this app changes often during dev, and cache-first was already bitten once by silently serving a stale `plex-netflix-card.js`). Cross-origin calls (Plex/YouTube/OpenRouter) bypass it entirely.
- `manifest.webmanifest` — PWA manifest. Currently `orientation: landscape`, `display: fullscreen` — inherited from the TV-kiosk HA use case. **Will need revisiting for phone/touch/Android use** (portrait, standalone vs fullscreen) once that platform is actually worked on.
- **Known gap:** `manifest.webmanifest` references `icons/icon-192.png` and `icons/icon-512.png` — that `icons/` directory doesn't exist yet (only `assets/plex-logo.png` is present). Needed before this installs cleanly as a PWA on any platform.

## Architecture invariant carried over from the HA version

**No backend, no proxy.** The card talks directly to Plex's HTTP API, the YouTube Data API v3, and the OpenRouter API from the browser/client. This was deliberately verified (not assumed) against Plex: it sends CORS headers back correctly *as long as the token is passed as a query param, not a header* — a header token triggers a preflight Plex won't answer. Keep this in mind before "cleaning up" any URL-building code to move the token into headers.

This trust model (bare API tokens visible in client-side config/devtools) was acceptable for a LAN-only HA panel. Revisit explicitly once Android/Xbox targets mean the app may be reachable off the home LAN — vault.js's at-rest encryption protects against *local* disk/backup exposure, not against the token being visible to anyone who can open devtools on an unlocked session.

## Technical gotchas worth knowing before touching Plex/YouTube integration code

- **Plex's `Genre` field on list endpoints is truncated to ~2 tags per item.** Per-item genre filtering alone is not reliable for anything genre-based (Kids Mode-style blocking, genre rows, etc.) — the original implementation had to add a second bucket-level check (does the *row's own source genre* match) independent of each item's own truncated tags.
- **The YouTube trailer embed uses the raw postMessage protocol, not the official `iframe_api`.** Sending a command (e.g. `pauseVideo`) before the player's own handshake has settled can leave the embed permanently stuck, unresponsive even to later real taps on YouTube's own UI. Any new command sent to that iframe needs to go through the existing handshake-then-command sequencing already in the file, not a fire-and-forget postMessage on `load`.
- **Cross-origin YouTube iframes need `referrerpolicy="strict-origin-when-cross-origin"` set directly on the `<iframe>`.** A page-level `<meta name="referrer">` policy that's too strict (as HA's frontend shipped) silently prevents YouTube from ever starting playback, with no on-screen error — verify via actual `videoplayback` network requests, not just "the player rendered."
- **Plex Android deep links** (`plex://libraries/<machine_id>/...`) are fully solved for movie/show/episode/collection/playlist — see the `plex_android_deeplink` reference. No "play now" intent exists on Android; the ceiling is landing on the item's details page. These links are Android-app-specific — gate on a UA check and fall back to a plain web link otherwise.
- **Shadow-DOM custom-element gotcha:** `mousedown` on a sibling element fires an input's `blur` *before* that sibling's `click` handler runs. Don't rely on the blur listener alone to collapse/close UI state that a click handler is also explicitly changing in the same gesture — do the explicit state change in the click handler itself.
- **Plex Home profile switching** (`plex-auth.js`'s `getHomeUsers`/`getCurrentUser`/`switchHomeUser`, wired up in `plex-netflix-card.js`'s sidenav "Profile" switcher) mixes two API generations - confirmed empirically against a real 4-profile Plex Home account. `getHomeUsers`/`getCurrentUser` work fine on the newer JSON `/api/v2/home/users` and `/api/v2/user`. The actual switch action does **not** live on `/api/v2/home/users/<id>/switch` (404) - it's the older `/api/home/users/<id>/switch`, same "old myplex endpoint, don't assume it honors `Accept: application/json`" situation as `/api/resources` elsewhere in this file. Still unverified: the exact response/error shape for a PIN-protected profile (a wrong or missing PIN) - if that path misbehaves, check the raw response before assuming the request shape is wrong. Also worth knowing: `discover.provider.plex.tv` (Watchlist) is plex.tv's *account*-level service and is called with `plex_account_token`, not the server-specific `plex_token` — mixing those up is an easy way to end up scoping Watchlist to the wrong identity after a profile switch.
- **Native playback (`plex-player.js` + Android's `NativePlayerPlugin`).** Because Plex authenticates via a query-param token rather than a header (see the CORS gotcha above), the native Media3/ExoPlayer side needs no custom HTTP header injection at all — the token is already baked into the URL handed to it. Progress/timeline reporting to Plex (`/:/timeline`) is deliberately kept entirely in `plex-player.js`, not duplicated into native code — the native plugin's only job is reporting raw position/state (`progress`/`ended`/`error` events) back to JS, one Plex-protocol implementation shared by both the native and `<video>`+hls.js fallback paths. Separately: WebView2 (used by the Xbox shell) has **no native HLS support**, same limitation as desktop Chrome — the `<video>`+hls.js fallback is required there too until a native MediaPlayerElement bridge exists for Xbox.

## Platform work not yet started

This scaffold only covers the web/desktop-mouse case (inherited as-is from the HA card). None of the following exist yet:

- **Touch.** The original card was resized for narrow viewports (mobile poster grid at 70% scale) but that was a *sizing* pass for viewing on a phone, not a touch-interaction pass — hover-dependent UI (mute/play button reveal, watchlist button hover state, row arrow visibility) needs an explicit touch-input audit.
- **Remote (Fire TV/Fire Stick).** Fire OS is Android-based; a Fire TV app is typically an Android TV-style app hosting this content in a WebView. Amazon's own Fire TV UX guidelines require full D-pad-only navigation (no feature may depend on hover or touch) with a clearly visible focus indicator on every focusable element. The Fire TV remote's D-pad/select/back are very likely delivered to the page as ordinary key events (arrow keys, Enter, Escape/Back-equivalent) rather than through the Gamepad API — **verify this empirically once real Fire TV hardware/emulator access exists**, don't assume. Nothing in this codebase currently has deliberate focus-based (as opposed to mouse-hover-based) navigation at all — hover-dependent UI (mute/play button reveal, watchlist button hover state, row arrow visibility) needs an audit before D-pad nav can work.
- **Controller (Xbox gamepad).** Nothing in this codebase currently reads the Gamepad API. **Worth checking early whether Xbox's own browser/PWA host already maps controller D-pad/thumbstick input to the same key-event-equivalent navigation Fire TV likely uses** (Microsoft's Xbox web-app guidance documents exactly this "gamepad-to-keyboard" behavior for D-pad/A/B in some Xbox browser/PWA contexts) — if so, the Fire TV and Xbox D-pad cases may collapse into one shared keyboard-equivalent focus-navigation implementation instead of two separate input systems (one key-event-based, one raw Gamepad-API-based). Confirm on real hardware before designing either. If a genuine raw Gamepad API path does end up needed (e.g. a physical Xbox controller paired to a phone/PC for this same app), watch for the double-handling trap noted in `feedback_double_handle_input_nav`: if the runtime already provides native focus navigation for those buttons, don't also run a custom polling handler for the same directions.
