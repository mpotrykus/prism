# Prism

A standalone rewrite of a Netflix-style Plex browsing dashboard, targeting **web, Android, Xbox, and PC**, with **remote (Amazon Fire TV/Fire Stick), touch, and controller (Xbox gamepad)** input support. The app itself is plain HTML/CSS/JS custom elements (no UI framework) — but it's built via **Vite** (`vite.config.js`, `base: "./"`, outputs to `dist/`) and wrapped natively per platform: **Capacitor** for Android (`android/`, package `com.mpotrykus.prism`), a **UWP + WebView2 shell** shared by Xbox and PC (`uwp/PrismUwp/`). Plain `dist/` output still works as a directly-served PWA for the web target.

## Origin

The UI (`src/card/card.js`) started life as `custom:plex-netflix-card`, a hand-written vanilla-JS Home Assistant Lovelace custom card running on a home server (`raspi-server`), browsing a personal Plex library with Netflix-style rows, a hero banner, search, Kids Mode, AI-generated genre rows, etc. That HA-hosted version is the **feature-complete reference implementation** — extensive build history (every feature, every bug, every fix) lives in this machine's memory for the `Desktop` project, not in this repo. If you need to know *how* an existing feature was originally built or why a specific decision was made, check there first — see `reference_dashboard_history` in the `Desktop` project's memory (it is not in this project's).

This repo is the rewrite: pull the card out of Home Assistant entirely so it can run as its own installable app on multiple platforms/input modes HA's Lovelace panel never had to support.

## Current state

- `package.json`/`vite.config.js` — the Vite build. `npm run dev`/`build`/`preview` for the plain web target; `npm run android` runs `cap sync android` then a Gradle debug build; `npm run uwp:sync` builds and copies `dist/` into the shared UWP shell's `www/` folder only (no `.msix`, same as `cap sync` not building an APK by itself); `npm run xbox:build` chains that plus an actual MSBuild restore+build, producing a sideloadable `.msixbundle` under `uwp/PrismUwp/AppPackages/`. MSBuild is located via `vswhere` (`scripts/xbox-build.mjs`), not a hardcoded Visual Studio path.
- `android/` — a committed, working Capacitor Android project (`com.mpotrykus.prism`). Hosts the same web app inside a `BridgeActivity` WebView, plus a native `NativePlayerPlugin`/`PlayerActivity` (Media3 ExoPlayer) bridged in from `src/player/player.js` for native-grade playback — see "Native playback" below.
- `uwp/PrismUwp/` — a UWP project hosting the same web app in a WebView2 control. Lives under `uwp/`, not `xbox/`, now that the folder itself is shared — only the deploy scripts (`scripts/xbox-build.mjs`/`xbox-deploy.mjs`, and the `xbox:build`/`xbox:deploy` npm scripts) keep the `xbox-`/`xbox:` naming, since those specifically produce/sideload a package for the Xbox console (Device Portal, `WinAppDeployCmd`) — nothing PC-specific needs an equivalent. Renamed from `PrismXbox` once it became the shared shell for both platforms (was already viable pre-rename: `Package.appxmanifest` declares only `Windows.Universal`, not `Windows.Xbox`, so nothing about the manifest itself was Xbox-only — see that file's own comment). Running it on a PC is just Visual Studio's local-machine debug target instead of Remote Machine → console; no separate project or branch needed. It now has a real native playback bridge (`uwp/PrismUwp/Player/NativePlayerHost.cs` + `PlayerBridge.cs`, driven from `src/player/xbox-bridge.js`) plus HDR, AI-upscaling and auto-crop paths, and `uwp/PrismUwpEffects/` for the D3D11 video effects. The JS chrome in `src/player/ui/` renders over the native video surface unchanged — the WebView2 sits transparent on top of it in one XAML page.
  - **Gamepad focus trap: confirmed on real hardware.** Opening the Xbox Guide (Nexus button) does not stop gamepad input from reaching the app underneath — both `MainPage.xaml.cs`'s `OnCoreWindowKeyDown` forwarder and `focus-nav.js`'s Gamepad API poller kept driving app navigation while the Guide overlay was open and being navigated with the same buttons. Fix in place, **not yet re-confirmed on hardware**: `MainPage.xaml.cs` now hooks `CoreWindow.Activated` (`OnCoreWindowActivated`) — `Deactivated` is the documented signal that another surface owns input — gates the native forwarder on it, and relays the state to the page via `window.__prismXboxInputActive` + an `xbox-input-active-change` CustomEvent, which `focus-nav.js`'s poller now checks before dispatching. Needs a real console re-test (open Guide, confirm app nav stops; close Guide, confirm it resumes) before considering this closed.
  - **Signing:** `npm run xbox:build` produces an unsigned package unless a matching cert exists — Xbox Dev Mode sideload rejects unsigned packages outright (`0x800B0100`). `PrismUwp_TemporaryKey.pfx`/`.cer` (self-signed, `CN=mpotrykus`, matching `Package.appxmanifest`'s `Identity Publisher`, password-less, ~20yr validity) are committed alongside the project — same convention Visual Studio uses by default for new UWP projects, referenced from `PrismUwp.csproj` via `PackageCertificateKeyFile`/`PackageCertificateThumbprint`. Signing the package is necessary but not sufficient: the Xbox console itself also has to **trust** this cert's root before it'll install the package — a signature check on an untrusted self-signed root fails differently (chain-validation error, not the "no signature" error) but still fails. Install `PrismUwp_TemporaryKey.cer` as a trusted certificate on the target console via its Device Portal (`https://<xbox-ip>:11443`, paired from the Dev Home app) before sideloading the `.msixbundle` — this is a one-time, per-console, manual step that can't be scripted from here.
  - **Deployment: use Visual Studio's "Remote Machine" debug target, not manual Device Portal sideload.** Confirmed working. A manual Device Portal upload of the `.msixbundle` requires separately uploading every framework dependency under `AppPackages/.../Dependencies/x64/` (5 files for this C# shell: `Microsoft.VCLibs.x64.14.00[.Desktop]`, `Microsoft.UI.Xaml.2.8`, `Microsoft.NET.Native.Framework.2.3`, `Microsoft.NET.Native.Runtime.2.3`) **in the exact same install request** — Windows validates the whole dependency closure atomically, so a request missing even one fails entirely and nothing from it persists, which makes adding dependencies one-at-a-time across separate attempts (in response to each new "framework could not be found" error) never converge. Opening `PrismUwp.sln` in Visual Studio and deploying to the paired Xbox as a Remote Machine target sidesteps all of this - VS provisions every framework dependency itself. `xbox-build.mjs` still builds **Release**, not Debug, since Debug's framework dependencies (`Microsoft.NET.CoreFramework.Debug.2.2`, `Microsoft.VCLibs...Debug.14.00`) are SDK-only debug redistributables that don't sideload cleanly even via the correct atomic-request approach.
  - **The two .NET Native framework dependencies are avoidable, just not for free.** `moonlight-xbox` (this machine's other Xbox UWP project, C++/CX) needs only `Microsoft.UI.Xaml`+`Microsoft.VCLibs` per its own README - no `.NET Native Framework/Runtime` at all, because those two are purely a byproduct of this shell being C#. A future C++/WinRT rewrite of this trivial WebView2 shell would drop the dependency count from 5 to 2 permanently, matching moonlight's proof - worth considering deliberately later, not a Phase 3 blocker now that Remote Machine deploy works.
  - **Microsoft Store submission (not needed for today's Xbox Dev Mode sideload path):** `Package.appxmanifest` declares the restricted `rescap:Capability Name="hevcPlayback"`. Xbox Dev Mode sideloading doesn't care, but the Microsoft Store certification pipeline does — restricted capabilities require a separate approval request in Partner Center before a submission using one will pass cert. Budget time for that request if/when this ever moves from sideload to an actual Store listing.
- `index.html` — shell: mounts `<streaming-plex-signin-modal>` and `<streaming-settings-modal>`, then loads `src/app.js` as its single module entry. Everything else is reached through that import graph.
- `public/` — copied verbatim into `dist/`: `sw.js`, `manifest.webmanifest`, icons, fonts, the Prism logo.
  - `manifest.webmanifest` is still `orientation: landscape` / `display: fullscreen`, inherited from the TV-kiosk HA use case. **Revisit for phone/touch use** (portrait, standalone vs fullscreen) — the rest of the touch work has moved on, this hasn't.
  - `sw.js` must only ever precache files that exist verbatim in `dist/`. It's a classic script, so it can't import `src/core/image-cache.js` — the cache names are duplicated in both and kept in sync by hand.

### Source layout (`src/`)

Everything is an ES module; there are no `window.Streaming*` globals.

- `src/app.js` — bootstrap. Registers the service worker, primes decode capabilities, creates a detached `<plex-netflix-card>`, wires `open-settings`/`settings-saved`/`request-plex-reauth`/`plex-connected` between the card and the two modals, and opens the sign-in modal (blocking) at boot when no server is configured.
- `src/constants.js` — frozen string-enums shared across files (`NAV_COMMAND`, `APP_EVENT`, `VIEW`, `MEDIA_TYPE`, `SECTION_TYPE`, …).
- `src/core/` — app-wide infrastructure with no UI of its own:
  - `config.js` — the plain-localStorage config store (`loadPlain`/`savePlain`/`loadFull`/`isConfigured`/`mergeServerTokens`). Deliberately separate from the Settings modal that edits it, so the data layer and subtitle providers can read config without importing an 800-line custom element.
  - `vault.js` — encrypts the sensitive fields (`plex_token`, `plex_account_token`, `openrouter_api_key`, `server_tokens`, OpenSubtitles credentials) at rest with a non-extractable AES key in IndexedDB. Deliberately *not* gated behind WebAuthn/biometrics: `plex_token` comes from Plex's own PIN sign-in rather than being hand-typed, so there's no local secret-entry step left to justify a Windows Hello / Android biometric prompt on every save and load.
  - `focus-nav.js` — the single document-level keydown listener plus the Gamepad API poller, normalising both into `NAV_COMMAND`s. Everything navigable registers through `wireLinearNav`/`registerNavHandler`.
  - `input-mode.js` — live "what is driving the app right now" (touch/mouse/keyboard), mirrored onto `documentElement`.
  - `html.js` (`escapeHtml`), `scroll-lock.js`, `image-cache.js`.
- `src/plex/` — direct plex.tv/PMS API access: `auth.js` (PIN sign-in, server + library discovery, Home profile switching), `subtitles.js`, `opensubtitles.js`.
- `src/settings/` — `modal-element.js` (the shared shadow-root/overlay base class), `settings-modal.js` (`<streaming-settings-modal>`), `signin-modal.js` (`<streaming-plex-signin-modal>`, which gates the app at boot and is reachable again from Settings' "Reauthenticate").
- `src/card/` — the browsing UI. `card.js` is the `<plex-netflix-card>` custom element and owns the shadow root; the rest are collaborators it calls into: `data.js` (all Plex fetching/orchestration), `rows.js`/`row-scroll.js` (poster rows), `hero.js`, `title-info.js`, `search-page.js`, `nav.js`, `profile.js`, `watchlist.js`, `pin.js`, `more-sheet.js`, `media-badges.js`, `youtube-embed.js`. `src/card/logic/` is the DOM- and network-free layer (catalog/search/trailer/tmdb/cross-server/deep-link) and is where the unit tests live. `src/card/styles/` holds the stylesheets, imported `?inline` and injected into the card's shadow root.
- `src/player/` — `player.js` is the `StreamingPlayerController` singleton and owns session state; every other module takes that instance as an explicit first argument. `native-bridge.js` (Android), `xbox-bridge.js` (UWP) and `web-fallback.js` (`<video>` + hls.js) are the three backends; `core/` holds the backend-independent Plex protocol (stream URLs, session reload, ABR, BIF, subtitles, wake lock, media facade); `ui/` is the on-screen chrome; `shader/` and the `*-pipeline.js` files are the GPU effects. `src/player/styles/` holds the chrome's stylesheets, injected once into `document.head` by `ui/styles.js` (it can't live in a shadow root — on Xbox it has to render over a native video surface).
- `src/styles/` — the app-level stylesheets outside the card's shadow root: `colors.css` (loaded by `index.html`), `modal-shell.css` and the two modal stylesheets.

### Conventions worth keeping

- **No forwarding layers.** `card.js` and `player.js` used to carry ~70 one-line methods that just called an imported function; those are gone. Call the module function directly and pass the card/controller instance as its first argument.
- **`escapeHtml` from `core/html.js`** is the only HTML-escaping helper. Don't re-roll it per file, and don't thread it through as a ctx callback.
- **Styling lives in CSS files**, not `Object.assign(el.style, …)`. The card's stylesheets are shadow-scoped; the player's are global and `prism-player-` prefixed.
- **Comments earn their place.** The Plex/WebView2/Android quirks in this codebase are hardware-verified and expensive to rediscover — keep those. Don't add comments that restate the code or narrate what a refactor changed.

## Architecture invariant carried over from the HA version

**No backend, no proxy.** The card talks directly to Plex's HTTP API, the TMDB API, and the OpenRouter API from the browser/client. This was deliberately verified (not assumed) against Plex: it sends CORS headers back correctly *as long as the token is passed as a query param, not a header* — a header token triggers a preflight Plex won't answer. Keep this in mind before "cleaning up" any URL-building code to move the token into headers.

This trust model (bare API tokens visible in client-side config/devtools) was acceptable for a LAN-only HA panel. Revisit explicitly once Android/Xbox targets mean the app may be reachable off the home LAN — vault.js's at-rest encryption protects against *local* disk/backup exposure, not against the token being visible to anyone who can open devtools on an unlocked session.

## Technical gotchas worth knowing before touching Plex/YouTube integration code

- **Trailer discovery is TMDB, not the YouTube Data API** (`src/card/logic/trailer.js` + `src/card/logic/tmdb.js`). `resolveTrailerVideo` still tries a Plex-hosted extra first; only once that misses does it fall back to TMDB's `/movie|tv/{id}?append_to_response=videos`, picking the best `site==="YouTube" && type==="Trailer"` entry (official > English > most recently published) and handing the resulting video id to the same YouTube `<iframe>` embed hero.js/title-info.js already use. An earlier version used YouTube's own `search.list`, which required every user to create and paste in their own YouTube API key just to get trailers — `search.list`'s 100-unit/day quota made that necessary but also made the app confusing to set up. TMDB's videos endpoint needs no search and barely any quota, so Prism bundles its own TMDB API key (`VITE_TMDB_API_KEY`, baked in at build time via `.env` — see `.env.example`) instead; `resolveTmdbTrailer` degrades to "no trailer" (not a throw) when that key isn't configured, e.g. in a from-source dev build without a `.env`. Getting the tmdb id for a Plex item requires a full `/library/metadata/{ratingKey}` fetch (list/hub responses don't reliably carry the `Guid` array — same truncation-style gotcha as `Genre` below) — an episode borrows its parent show's tmdb id/trailer rather than having its own. Resolved trailers are cached in localStorage (`prism.trailerCache`, keyed `movie:<id>`/`tv:<id>`) so a title's info panel doesn't re-hit TMDB on every open; a "no trailer found" result is cached too, but with a shorter TTL and only once TMDB was actually queried (never for an unconfigured/missing key), so a title genuinely re-checks once TMDB might have added one.
- **Plex's `Genre` field on list endpoints is truncated to ~2 tags per item.** Per-item genre filtering alone is not reliable for anything genre-based (the HA reference implementation's now-removed Kids Mode content-blocking relied on this, as would any future genre-based feature) — the original implementation had to add a second bucket-level check (does the *row's own source genre* match) independent of each item's own truncated tags.
- **The YouTube trailer embed uses the raw postMessage protocol, not the official `iframe_api`.** Sending a command (e.g. `pauseVideo`) before the player's own handshake has settled can leave the embed permanently stuck, unresponsive even to later real taps on YouTube's own UI. Any new command sent to that iframe needs to go through the existing handshake-then-command sequencing already in the file, not a fire-and-forget postMessage on `load`.
- **Cross-origin YouTube iframes need `referrerpolicy="strict-origin-when-cross-origin"` set directly on the `<iframe>`.** A page-level `<meta name="referrer">` policy that's too strict (as HA's frontend shipped) silently prevents YouTube from ever starting playback, with no on-screen error — verify via actual `videoplayback` network requests, not just "the player rendered."
- **Plex Android deep links** (`plex://libraries/<machine_id>/...`) are fully solved for movie/show/episode/collection/playlist — see the `plex_android_deeplink` reference. No "play now" intent exists on Android; the ceiling is landing on the item's details page. These links are Android-app-specific — gate on a UA check and fall back to a plain web link otherwise.
- **Shadow-DOM custom-element gotcha:** `mousedown` on a sibling element fires an input's `blur` *before* that sibling's `click` handler runs. Don't rely on the blur listener alone to collapse/close UI state that a click handler is also explicitly changing in the same gesture — do the explicit state change in the click handler itself.
- **Plex Home profile switching** (`src/plex/auth.js`'s `getHomeUsers`/`getCurrentUser`/`switchHomeUser`, wired up in `src/card/card.js`'s sidenav "Profile" switcher) mixes two API generations - confirmed empirically against a real 4-profile Plex Home account. `getHomeUsers`/`getCurrentUser` work fine on the newer JSON `/api/v2/home/users` and `/api/v2/user`. The actual switch action does **not** live on `/api/v2/home/users/<id>/switch` (404) - it's the older `/api/home/users/<id>/switch`, same "old myplex endpoint, don't assume it honors `Accept: application/json`" situation as `/api/resources` elsewhere in this file. Still unverified: the exact response/error shape for a PIN-protected profile (a wrong or missing PIN) - if that path misbehaves, check the raw response before assuming the request shape is wrong. Also worth knowing: `discover.provider.plex.tv` (Watchlist) is plex.tv's *account*-level service and is called with `plex_account_token`, not the server-specific `plex_token` — mixing those up is an easy way to end up scoping Watchlist to the wrong identity after a profile switch.
- **Native playback (`src/player/player.js` + Android's `NativePlayerPlugin`).** Because Plex authenticates via a query-param token rather than a header (see the CORS gotcha above), the native Media3/ExoPlayer side needs no custom HTTP header injection at all — the token is already baked into the URL handed to it. Progress/timeline reporting to Plex (`/:/timeline`) is deliberately kept entirely in `src/player/player.js`, not duplicated into native code — the native plugin's only job is reporting raw position/state (`progress`/`ended`/`error` events) back to JS, one Plex-protocol implementation shared by both the native and `<video>`+hls.js fallback paths. Separately: WebView2 has **no native HLS support**, same limitation as desktop Chrome — which is why the UWP leg asks Plex for a progressive stream (`protocol=http`, `start.mp4`) and hands it to the native player instead. See `src/player/core/platform.js`'s `usesProgressiveStream`.

## Input modes

- **Controller (Xbox gamepad) — built.** `src/core/focus-nav.js` runs both paths against one shared per-command cooldown: a document-level capture-phase keydown listener, and a `requestAnimationFrame` Gamepad API poller that translates D-pad/stick/A/B/bumpers/triggers/Start/Select into synthetic key events fed through that same pathway. Building both against one cooldown sidesteps having to know up front whether a given host delivers D-pad input as real key events, raw gamepad state, or both — a single physical press that produces both is deduped rather than double-navigating (the trap noted in `feedback_double_handle_input_nav`).
- **Remote (Fire TV/Fire Stick) — untested.** Fire OS is Android-based, so a Fire TV build would be an Android TV-style app hosting this in a WebView. It should already work through the same keyboard-equivalent path as the Xbox leg, but **that has never been verified on real hardware or an emulator.** Amazon's UX guidelines require full D-pad-only navigation with a visible focus indicator on every focusable element, which `wireLinearNav` provides.
- **Touch — partially done.** `src/core/input-mode.js` tracks the live input mode and mirrors it onto `documentElement`, and `responsive.css` covers narrow viewports (including the mobile Libraries sheet and the bottom nav bar). Hover-dependent affordances that still need a deliberate touch pass: the hero's mute/play reveal and the per-poster watchlist button.
